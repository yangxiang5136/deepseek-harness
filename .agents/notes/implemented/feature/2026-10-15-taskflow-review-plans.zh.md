# Agent Note: TaskFlow 审阅计划标明聊天并保留精确债务

Status: implemented

[English](2026-10-15-taskflow-review-plans.md) | 中文

## Problem

注意力账本记录执行活动和等待人工决定的事项，但无法表达相关材料值得按什么顺序审阅。步骤描述不能标明应该回看的聊天，而多个步骤可能属于同一聊天。按任务名排列债务也会混淆共用同一任务的不同审阅请求。另一聊天出现新信息而计划尚未吸收时，已保存的顺序可能造成误导。

## Decision

项目审阅计划以独立的本地 JSON 文件保存，由 TaskFlow 宿主读取。客户端校验文件，按已保存的顺序和明确的排序覆盖显示真实聊天名称，并单列可并行的聊天。同一聊天 ID 的多个步骤合为一行。缺少聊天名称时明确显示等待同步，不用步骤描述代替。步骤描述、理由、条件和引用仍作为计划元数据保留。只有计划、没有近期活动、待办或债务的项目，也能通过项目选择器进入。

每个条目引用精确的 schema-v2 债务事件 ID，聊天行合并显示这些债务的审阅状态。审阅列表不提供复制入口或打开债务的按钮；原有待收口托盘负责打开和收口每条精确债务，即使多条债务共用同一任务短语也不混淆。项目树保留活动历史，不再显示主线与分支的占比。审阅状态来自账本：普通终态事件保留未收口债务；现有的人工作出明确手势的审计收口只关闭精确目标；精确 supersede 记录替代关系。缺失的目标仍明确显示为待核对。[注意力账本决策](2026-08-15-taskflow-attention-bar.md)继续负责执行与收口语义。

保存的来源记录区分已观察消息与已核对消息。pending 记录说明有新信息等待核对，不批准材料或关闭任务。本机监听覆盖范围和扫描健康状态独立于这些来源记录显示；监听未接入、过期或失败时明确提示。计划读取随现有轮询节奏刷新。读取或校验失败时保留最后一份有效计划并显示错误，损坏的元数据不能静默清空审阅顺序。

## Alternatives considered

**向注意力事件加入排序和消息字段。** 六事件协议分别负责执行与精确收口。把计划更新编码为任务完成或新增审阅债务，会改变原义并制造虚假的工作或接受记录。

**把计划复制成待办勾选项。** 这会增加另一份可变的完成清单，且丢失精确债务身份、条件顺序和来源新鲜度。[项目入口决策](../bug-fix/2026-10-07-taskflow-project-access.md)保留待办入口；审阅建议使用独立数据。

**把任务名或新消息当作接受。** 多个审阅请求可能共用一个任务，新讨论也可能带来尚未解决的问题。只有明确的债务 ID 和现有收口操作，才能确定用户关闭了哪项待处理请求。

## Consequences

面板提供共享的本地审阅顺序，不改变账本 schema、通用 writer、收口手势或历史记录。它不向模型发送计划或聊天内容。写入方仍负责保存获准的元数据和准确来源；面板不截取外部应用消息，也不独立证明消息已经核对。

装配后的无密钥 Web 场景使用合成的完整聊天名称，检查名称准确显示、同一聊天去重、审阅列表没有操作按钮和分支占比、托盘中同任务债务的精确打开、页面持续打开时的计划更新、来源新鲜度标签、最后有效计划保留，以及现有收口往返。顺序属于建议，不是调度：保存、阅读、讨论或重排条目，都不构成批准、完成或执行该项工作的授权。
